**🕒 03:23 👤 @trey.io (Trey Hunner)**
💬 Python Tip #248 (of 365):

Run "pytest --pdb" to drop into PDB when a test fails. 🧵

With "--pdb", pytest starts PDB in post-mortem mode (see tip #169) as soon as a test fails or raises an exception.

#Python #DailyPythonTip

[Открыть пост](https://bsky.app/profile/trey.io/post/3mut25zypa32r)

----
**🕒 03:23 👤 @trey.io (Trey Hunner)**
💬 Here's a failing test with "--pdb":

calculate‍.py:2: TypeError
>>> PDB post_mortem >>>
-> total = sum(amounts)
(Pdb) amounts
['3.49', '13.89']

We're paused inside the function that raised the exception and we can poke at local variables and such.

**🕒 03:23 👤 @trey.io (Trey Hunner)**
💬 I find this much nicer than sprinkling print calls through a test and re-running it.

You can inspect objects, call functions, walk up the stack, and poke at things in real time instead of re-running repeatedly.

**🕒 03:23 👤 @trey.io (Trey Hunner)**
💬 Two flags that pair nicely with --pdb:

• -x: stop after the first failure (so you're debugging ONE problem at a time)
• --lf: rerun only the tests that failed last time

$ pytest --pdb -x --lf

**🕒 03:23 👤 @trey.io (Trey Hunner)**
💬 breakpoint() works in tests too. Put one in a test (or in the code it tests) and run pytest as usual: it'll pause there and hand control to PDB.

But when the question is "why did THIS test fail?", I usually reach for "pytest --pdb" first.
