**🕒 06:28 👤 @trey.io (Trey Hunner)**
💬 Python Tip #328 (of 365):

Use a linter and an auto-formatter. 🧵

Linters are stylistic proofreaders for your code. They spot inconsistencies, and sometimes bugs:

$ ruff check greet‍.py
F401 [*] `os` imported but unused
 --> greet‍.py:1:8
help: Remove unused import: `os`

#Python #DailyPythonTip

[Открыть пост](https://bsky.app/profile/trey.io/post/3n34jrjoknv2w)

----
**🕒 06:28 👤 @trey.io (Trey Hunner)**
💬 Auto-formatters do a bit more: instead of just noting issues, they restyle your code for you.

$ ruff format --diff greet‍.py
-    print( message )
+    print(message)

Some linters include an auto-formatter, and some tools only auto-format.

[Открыть пост](https://bsky.app/profile/trey.io/post/3n34jrjszce2b)

----
**🕒 06:28 👤 @trey.io (Trey Hunner)**
💬 The setups I recommend, in order of preference:

• ruff for linting ("ruff check") and auto-formatting ("ruff format")
• flake8 for linting and black for auto-formatting
• pylint for linting and black for auto-formatting

Those aren't the only options, but they're the ones I most often recommend.

💬 To alert you have have software update, Ubuntu starts gnome-software in the background. 

It's the software to manage their app store, and it doesn't have a light mode for just checking updates, it loads the entire catalogue in memory, which on my machine, eats 2.4 Gb of ram all the time.

**🕒 14:51 👤 @bitecode.dev (Bite Code!)**
💬 To avoid that, create a dummy ~/.config/autostart/org.gnome.Software.desktop with:

[Desktop Entry]
Type=Application
Name=Software
Hidden=true

This will override the system one.

**🕒 22:00 👤 @trey.io (Trey Hunner)**
💬 Python Tip #329 (of 365):

Make sure your tests can actually fail. 🧵

This test passes no matter what calculate_total returns:

def test_total():
    total = calculate_total([3.50, 13.75])
    assert (total == 17.25, "wrong total")

#Python #DailyPythonTip

[Открыть пост](https://bsky.app/profile/trey.io/post/3n365tkjhr22y)

----
**🕒 22:00 👤 @trey.io (Trey Hunner)**
💬 Those parentheses make a tuple, which is always truthy.

A test that could never fail is worse than no test at all, because it provides false confidence.

Modern Python versions will print a warning about that tuple assertion, but most always-passing-test scenarios won't issue a runtime warning.

[Открыть пост](https://bsky.app/profile/trey.io/post/3n365tkmbgy25)

----
**🕒 22:00 👤 @trey.io (Trey Hunner)**
💬 A test may never run because its name doesn't start with test_. A test may mock so much that the code under test never runs.

And even if your code RUNS, you might accidentally make assertions that aren't actually useful.

So, break your code and watch your test fail.

[Открыть пост](https://bsky.app/profile/trey.io/post/3n365tkofyu2w)

----
**🕒 22:00 👤 @trey.io (Trey Hunner)**
💬 This is called red-green-refactor: write a failing test and THEN fix your code to pass the test.

In general, for every test, I'd ask yourself:

• Does it test the intended behavior?
• Does it exercise the code paths you think it does?
• Would it fail if the code broke?
